# 军团独占跟踪与项目结构审查

日期：2026-09-21

## 结论

本次审查聚焦玩家情报、军团与角色跟踪、客服区服权限、角色修改删除及账号管理调用链，不代表全项目安全审计。

新增军团独占跟踪沿用现有登录和区服权限：同一区服、同名军团只能由一名客服跟踪；不同区服同名军团相互独立。军团归属与成员个人归属独立，不批量改变成员的跟踪关系。

现有结构可以继续扩展，但应优先解决共享角色删除和角色跟踪释放问题，再做代码拆分与查询优化。本次没有顺带改变已有角色删除、成员跟踪和账号停用规则。

## 优先优化项

### P1：共享角色删除会影响其他客服的历史数据

- 位置：[character-edit.server.ts](E:/project/aion2web/src/server/character-edit.server.ts:17)、[聊天外键](E:/project/aion2web/migrations/0005_account_scoped_chat_history.sql:24)、[消息外键](E:/project/aion2web/migrations/0005_account_scoped_chat_history.sql:52)。
- 触发条件：客服 A 有区服权限，角色没有被其他客服主动跟踪；即使客服 B 已经和这个角色聊天，A 仍能删除共享角色。
- 当前行为：执行物理删除后，所有客服关联会话、消息和角色跟踪备注随外键级联删除。当前弹窗已告知这个影响，但确认弹窗不能替代共享数据的权限隔离。
- 建议：普通客服只允许移出个人名单；共享角色改为软删除，并提供恢复入口。永久清除限定管理员执行，记录操作者和影响范围。
- 验收：A 的普通删除操作不能抹掉 B 的历史；管理员归档和恢复后，角色与历史关联保持一致。

### P1：现有角色跟踪缺少异常归属释放入口

- 位置：[账号停用](E:/project/aion2web/src/routes/api/admin/accounts.ts:44)、[角色权限检查](E:/project/aion2web/src/routes/api/character-tracking.ts:27)、[角色跟踪写入](E:/project/aion2web/src/server/character-tracking.server.ts:46)。
- 触发条件：A 跟踪角色后被停用，或者管理员撤回 A 的区服权限。
- 当前行为：旧角色跟踪仍为 active；A 无法再调用释放接口，其他客服也不能接手，现有角色跟踪接口没有管理员释放他人归属的分支。重新启用或重新授权可绕回，但不适合作为常规处理方式。
- 建议：为角色跟踪补充管理员释放/移交入口、版本校验和审计记录。停用/撤权时提示尚有多少跟踪资源需要处理，不静默自动抢占。
- 本次新军团跟踪已提供管理员释放和版本保护；旧角色跟踪仍需单独补齐。

### P2：排行榜查询重复计算，目录也走排名流程

- 位置：[intelligence.server.ts](E:/project/aion2web/src/server/intelligence.server.ts:29)。
- 当前行为：列表和总数使用两条带窗口排名的查询，军团目录也构建排名窗口；翻页继续对授权范围计算排名，并使用 OFFSET 跳过前面的结果。
- 风险：数据量和页数增大后，扫描、排序及数据库读取成本增长。本次没有做生产压测，不能据此断言当前已经出现性能瓶颈。
- 建议：目录使用独立聚合查询；总数查询不计算排名；榜单再考虑按区服生成定期快照，同时显示快照时间，固定分页期间的名次。
- 保留现有正确行为：权限过滤必须在排名前完成，名称搜索必须在排名后完成。

### P2：军团排行榜只移除了页面入口，后端仍接受该类型

- 位置：[intelligence.server.ts](E:/project/aion2web/src/server/intelligence.server.ts:11)。
- 当前行为：页面没有“军团排行榜”，但 API 仍接受 `view=guilds` 与平均战斗力指标。
- 影响：界面和接口的功能定义不一致，后续仍需维护和测试用户已取消的分支。这本身不构成越权，接口仍有区服权限检查。
- 建议：确认是否需要兼容旧调用；若无调用方，删除后端分支和对应测试。未来榜单统一由视图定义配置驱动。

### P2：主页面承担过多职责

- 位置：[index.tsx](E:/project/aion2web/src/routes/index.tsx)。本次审查时约 3,851 行。
- 当前职责包含登录后页面框架、客户端选择、消息同步、私聊和批量发送、AI 托管编排、角色资料页面及接口文档。
- 风险：功能耦合较多，一个页面交互变化容易牵涉消息和客户端状态；难以仅对某个业务模块做小范围验证。
- 建议：按角色资料、消息中心、客户端操作、接口文档拆分组件；发送与消息同步提取为独立 hook/service。页面入口只负责组装和导航，不一次性重写。

### P2：军团目前缺少独立、稳定的身份编号

- 位置：[玩家情报军团聚合](E:/project/aion2web/src/server/intelligence.server.ts:27)、[新增军团跟踪表](E:/project/aion2web/migrations/0019_guild_tracking.sql:2)。
- 当前依据：角色记录中的 `server_id + legion_name`。
- 限制：无法可靠判断“军团改名”和“新建了同名军团”是不是同一实体，也无法区分“暂时没有收录成员”和“游戏中已解散”。
- 建议：采集端能提供稳定军团 ID 后，建立独立 guilds 表，再迁移跟踪关系；当前不靠猜测合并军团。
- 本次处理：即使目录里暂时没有成员，跟踪记录仍保留在管理列表中，可以由本人或管理员释放，避免无入口的占用。

## 新军团跟踪结构

```text
玩家情报页面
  ├─ 军团卡片：显示跟踪归属
  ├─ 军团详情：跟踪 / 取消跟踪
  └─ 我的军团跟踪 / 管理员跟踪管理
        ↓
GuildTrackingProvider：一次加载归属，操作后刷新，15 秒轮询及窗口恢复刷新
        ↓
/api/guild-tracking：登录检查、来源检查、参数校验、区服权限
        ↓
guild-tracking.server：原子认领、本人释放、管理员释放、版本校验
        ↓
guild_tracking：区服 + 军团名称复合主键，只有一个所有者槽位
guild_tracking_events：触发器同步记录认领与释放，操作者来自登录身份
```

### 冲突与释放规则

1. A 跟踪后，B 看到 A 的归属，不能再次认领。
2. 即使 B 的页面尚未更新，服务端也拒绝重复认领。
3. 普通客服只能释放自己的军团，管理员可以显式释放他人归属。
4. 释放使用页面读取到的版本号；如果别人已经释放并重新认领，旧操作会失败，不会误释放新所有者。
5. 释放后保留版本及审计记录，不物理删除所有权槽位。
6. 军团跟踪不自动占用全部成员；原有成员的跟踪、私人备注与聊天权限保持原规则。

## 建议推进顺序

1. 先明确并收紧共享角色删除权限，增加归档/恢复。
2. 给旧角色跟踪补齐管理员释放与审计。
3. 清理已取消的军团排行榜接口，减少无用分支。
4. 拆分主页面职责，优化榜单读取。
5. 采集端具备稳定军团 ID 后再升级军团数据模型。
