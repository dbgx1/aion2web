## 本次修复

1. **目录共享请求和短期缓存**：门户与消息页使用同一浏览器资源，合并并发请求；60 秒内重新挂载复用结果。没有新增周期刷新；手动刷新仍读取最新目录，导入过程中的强制刷新会等待当前请求后重新读取。服务端渲染不填充此缓存，API 仍先鉴权。
2. **占用轮询按需执行**：仅在相关界面可见时轮询；后台空闲或离线时跳过。后台正在群发时仍检查占用，保留权限丢失时停止任务的行为。失败后退避，最长 60 秒，恢复可见/网络时触发检查。
3. **消息保存单次执行及退避**：跨消息数组变化保留进行中标记，避免重渲染启动重叠保存；15 秒请求超时；失败重试间隔从 5 秒逐步增加至 5 分钟。HTTP 429 保留重试，不作为永久成功处理。
4. **消息写入幂等**：先按会话和来源 ID 查询已存消息，跳过重复及批内重复；数据库唯一约束仍用于竞争保护。已存在会话不再每批 UPSERT，预览只有内容/时间等实际需要更新才写，旧消息重放不会倒退预览。
5. **在线查询完成幂等**：完成更新加 `finished = 0` 条件，避免重复结果反复修改已完成记录。已有的可见角色窗口查询、隐藏页面停止在线状态轮询继续保留。
6. **日志采样由 100% 改为 10%**：减少常态日志事件量。采样也可能遗漏错误请求，排障时可短期提高；这不是保留全部错误日志的配置。

作为规模示例，5 秒一次的轮询若全天运行，每个标签页约 17,280 次请求/天。隐藏空闲页面停止后可省去这部分请求；实际节省取决于打开页面的时长和人数，不等于所有请求都下降同一比例。

## 计费解释

官方规则核对日期：2026-09-04。套餐共享额度、其他 Worker 用量及最终账单尚未核实。

- [D1 定价](https://developers.cloudflare.com/d1/platform/pricing/)：Free 每天 500 万读取行、10 万写入行、5 GB；Paid 每月包含 250 亿读取行、5,000 万写入行和 5 GB，超额分别为 $0.001/百万读取行、$1/百万写入行、$0.75/GB·月。索引更新也计写入行，读取按扫描行而非返回条数统计。免费套餐额度并非自动付费透支额度。
- [Workers 定价](https://developers.cloudflare.com/workers/platform/pricing/)：Standard 每月包含 1,000 万请求和 3,000 万 CPU 毫秒；超额为 $0.30/百万请求和 $0.02/百万 CPU 毫秒。等待网络响应不等于 CPU 运行时间。账户套餐基础费用另计。
- [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)：Paid 每月包含 2,000 万日志事件，超额 $0.60/百万事件；Free 每天 20 万事件。采样率控制被采样请求的日志，不是金额上限。
- [D1 指标说明](https://developers.cloudflare.com/d1/observability/metrics-analytics/)：查询分析用于定位热点，实际操作可从 D1 返回的 meta 观察 rows_read/rows_written；自适应聚合不应当作逐笔账单。

因此“今天读了约 1,248 万行”不能直接等同于高额账单。若使用 Paid 且没有其他大量共享消耗，单这一规模远低于月度包含读取量；若使用 Free，则需关注每日限额带来的服务不可用风险。

## 补充复核：消息批量与失败路径

| 发现 | 修改 | 验证依据 |
| --- | --- | --- |
| 消息数组每次变化都会立即保存，连续事件绕过批量窗口 | 改用固定 5 秒窗口，React `useEffectEvent` 读取最新消息；空批次不发请求；上传串行，临时故障停止本轮后续批次 | 实际门户浏览器中 20 次消息更新只发 1 次 POST；250 条积压遇到 503 只发第一批 |
| 只按条数拆包，包含中文、emoji、转义字符或大型 raw 的请求超过 512 KiB 后不断失败 | 新增 `message-sync.ts`，按完整 JSON 的 UTF-8 字节数拆包，同时保留每组 50 条、每请求 100 条及 25 组限制；单条超限隔离并提示未保存 | 字节边界测试覆盖恰好 512 KiB、超出 1 字节、大型 raw、500 条及多会话；相邻正常消息保留 |
| HTTP 400/404 被标记为已保存；不完整成功响应缺乏逐会话确认 | 只有身份、消息数及 `ok` 匹配的确认才能标为已保存；永久拒绝另行记录，显示错误及手动重试；401 暂停保存 | 实际门户测试拒绝与缺失确认后可重试，成功确认后不再重复上传 |
| 消息接口先完整读入请求再判断大小 | 流式累计真实字节数，超过限制立即取消读取；继续保留鉴权及 Content-Length 快速拒绝 | 无 Content-Length 的无限输入流在超限时返回 413，取消读取且不访问数据库 |
| 在线状态支持 500 个角色，却在单条 SQL 绑定最多 1,000 个参数 | 按 50 个角色拆分查询，去重读取、保持原输出顺序 | SQLite 适配器强制检查每次不超过 100 参数；500 条和重复输入均通过。平台限制见 [D1 Limits](https://developers.cloudflare.com/d1/platform/limits/) |
| 在线状态读取无超时，失败仍每 10 秒请求；保存失败连续立即尝试三次 | 15 秒超时、离线暂停、20 秒起的指数退避（最长 5 分钟），筛选变化不清空退避；结果保存遇永久拒绝立即停止，临时失败间隔 1 秒、2 秒后重试，最多三次 | 实际 hook 浏览器测试覆盖滚动、离线/恢复网络、400 以及 503 重试间隔 |
| 离线上报失败时，其他客户端心跳不断再次触发同一请求 | 增加 10 秒超时及 5 秒起、最长 60 秒的退避；永久拒绝不重试，仍保留原有 60 秒报告有效期 | 实际 MQTT hook 模拟离线上报 503 后连续 10 个其他心跳，仅发出一次上报 |

这组修改减少的是可避免的请求、失败重试和数据库访问，不承诺固定账单降幅。消息在界面上仍即时出现，**落库最长新增约 5 秒批量等待**，失败后还需等待退避。后台仍保存收到的消息，避免把“省轮询”误用于停止保存。

## 尚未解决的预算边界

- 未设置账户费用硬上限。当前授权不能读取订阅账单；也没有取得足够的生产 CPU 分布来安全压低单请求 CPU 上限。CPU 上限仅约束单次请求，不是整个账户金额封顶。
- 目录仍由 D1 聚合，全量 COUNT 和包含式文字搜索仍可能扫描较多行。若新版之后仍为热点，再引入可失效的汇总数据；目前不为省少量读取额外引入付费服务和复杂写入同步。
- 多用户、多标签页会分别消耗请求；前端节流不能阻止直接调用 API。登录和上传鉴权保留，但未新增按用户/账户的服务端请求配额或全站预算熔断。开放注册及 AI 接口应单独做额度策略。
- AI 实际使用 **OpenRouter**，不是 Workers AI。输出 token 有上限，但没有每日/每用户金额配额，输入也缺少独立预算控制；这是外部供应商的费用风险，不能混入 Cloudflare 账单或宣称已解决。
- 已实现按字节拆包，但尚未实施持久化待发送队列。浏览器 500 条事件缓存仍存在未保存消息被挤出的风险，关闭、刷新页面也可能失去未保存消息；“重试保存”仅处理当前页面仍保留的消息。高吞吐、长时间服务不可用或严格不丢消息的场景仍需独立持久化 outbox / 可信桥接端落库，不能把本次批量优化理解为投递保证。
- 角色、消息及在线查询历史继续增长，尚无业务保留期限；本次未擅自删除历史。需要明确保留期限后再处理归档/清理。
