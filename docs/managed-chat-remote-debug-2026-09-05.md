## 已确认的逻辑缺口

1. 服务端虽通过提示词要求托管执行发送，却未设置工具选择约束；模型可正常结束并仅输出文字。客户端发现 `acted === false` 后抛出截图中的通用错误，调度器按 60、120、240、480、900 秒退避，因此会呈现“失败后等待”。
2. 真实 ChatClient + SSE 回归回放证明：发送工具抛错后，SDK 可以继续请求模型；原实现未在该处立即停止，会延长本轮并可能把发送失败掩盖成后续结果。

## 修复

- 托管在尚未调用聊天动作时使用 `modelOptions.toolChoice: 'required'`，经真实 OpenRouter SDK 序列化测试确认线上请求字段为 `tool_choice: required`。普通交互聊天仍可回答文字。
- 兼容旧页面：历史已包含私聊/群发动作时，不强迫后续总结再执行动作，避免群发排队后出现额外发送。
- 正常结束但没有聊天动作时，客户端最多纠正一次。纠正请求只提供私聊与群发动作，保留原固定角色范围及原任务；不把纯文字输出直接发送给玩家。
- 上游报错、发送失败、取消不进入“无动作纠正”。发送失败立即停止 SDK，保留原始错误给调度器；成功发送或完成群发排队也停止额外模型总结。
- 浏览器控制台新增 `[managed-ai]` 结构化摘要：耗时、请求数、工具名、是否纠正、是否尝试动作及结果；不记录聊天正文、角色标识、参数、凭据或原始供应商数据。
- 保留工作区中原有的调度器、回执重试及相关测试修改，未改动用户配置或切换模型。

## 16:28–16:34 心跳：捕获在线过期导致全局退避，已补充修复

- 监控先观察到确认发送从 88 增至 97，近期摘要出现发送工具已被调用但失败的记录。扩大无正文摘要样本至 107 条，其中 104 条确认送达、3 条错误，均为一次请求、`send_private_chat`、已尝试动作但未完成；不是“未调用发送工具”。
- 随后页面在确认发送 104 条时显示：`请求失败，将退避后自动重试：角色在线状态已过期或已离线，等待重新查询（16:30:43 后重试）`。这次取得了明确的页面错误原因。后续自行恢复至 126 条，未刷新或重启托管。
- 根因是调度竞态：选择角色时在线缓存仍有效，AI 生成/占用校验期间越过 180 秒有效期，发送前检查正确阻止发送，但异常被并入全局 AI/发送退避，还会把主动聊天错误加入回复队列。
- 改用 `ManagedPresenceUnavailableError`，在发送前保存该错误，即使 SDK 吞掉工具异常也不会误计为成功。它仅暂缓受影响角色，不增加全局失败计数、不设置全局重试时间、不伪造新私聊；实际待回复消息继续保留。
- 在线状态过期时安排正常查询，并让其他在线角色继续处理。已确认离线的鲜活缓存不会被立刻反复查询；已有在线查询服务失败的退避也不会被绕过。诊断结果单列 `presence_changed`。
- 新增确定性回归覆盖：生成中缓存过期、生成中改为离线、SDK 吞异常、另一角色在查询期间继续发送、重新在线后加入、主动/回复身份、真实查询失败仍退避。在线、SDK 纠正、调度器、回复延迟、真实门户/SSE/MQTT UI 回归全部通过；类型检查、构建和 diff 检查通过。
