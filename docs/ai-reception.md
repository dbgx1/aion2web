# 玩家智能接待：实施与运营

## 使用入口

- **AI 接待台 → 内容与规则**：保存当前客服账号的聊天风格、已确认业务资料、Guide 和 Discord 信息。
- **AI 接待台 → 模拟对话**：使用真实 AI 和已保存内容库，多轮验证回复与判断；不发送游戏消息、不建立真实交接工单。
- **实时消息 → AI 助手 → 持续托管模式**：接待方式默认“智能接待”。选择当前角色或固定筛选范围，开启后收到玩家消息才处理。
- **AI 接待台 → 接待队列**：查看需求摘要、原话证据、商业/支持意图与发送审计。等待真人优先排列。
- 点击**真人接管**后，可直接**打开玩家私聊**。接管阻止该角色尚未授权的 AI 发送；已经提交给游戏客户端的命令无法撤回，应结合回执核对。
- 完成真人处理后可**交回 AI**，由下一条玩家消息触发；或**结束会话**。结果不确定的发送必须先人工确认已送达或未送达。

## 决策架构

现有 MQTT 客户端收消息 → 固定范围的托管调度器 → `/api/ai/reception` → D1 去重与会话版本 → TanStack AI 结构化决策 → 硬规则检查 → 保存候选 → 发送前原子认领 → 现有游戏发送与回执 → 持久化实际结果。

每轮一个主要动作：回答、追问、Guide、Discord、询问转接、真人交接、等待或结束。玩家困难不等于商业意图；询价、购买和支持问题保留原话证据。需要真人且有明确请求或同意时，创建等待真人状态，AI 停发。

模型使用项目现有 OpenRouter 通道及 `deepseek/deepseek-v4-flash-0731`，关闭推理模式以控制接待延迟，遵循 Zod 输出约束；关闭 SDK 网络自动重试，单次模型请求限时 25 秒。若决策被规则拦截，最多纠正一次，整轮限时 55 秒。玩家消息和内容库属于数据，不得改变规则。新的智能接待风格独立于旧自由托管人设，默认跟随玩家语言、自然简短、不冒充真人。

服务端规则检查包括：接管/结束状态、当前消息方向、商业与交接原话证据、邀请拒绝、重复资源、链接白名单、重复回复、最多一个问题。模型判断仍可能出错；模拟回放和决策审计用于持续评估，不将置信度当成事实。

## 数据与协作

迁移 `0016_ai_reception.sql` 添加三张表：

- `reception_settings`：每个客服独立的资料和风格。
- `reception_profiles`：按区服和角色共享的需求记忆、拒绝记录、接管状态、已发内容、最后决策和版本。
- `reception_turns`：按区服、角色、玩家消息唯一去重，保存输入记录、候选、拦截原因和回执状态。

API 每次验证登录与区服权限。其他接待员只能查看和接管自己有权限区服的角色；发送认领与自动回执还必须属于原调用账号。人工核对允许同区服接待员处理。内容配置只能改当前账号。

“准备发送”与“实际送达”分开：Guide 与 Discord 的已发记录只在成功回执或人工确认送达后更新。多个标签页/账号不能重复认领同一轮；新决策或人工接管使旧版本失效。结果不确定时不自动重发，进入人工核对。页面中断后超过两分钟的发送/生成会在读取接待队列时转为待处理。

## 运行边界

智能接待沿用现有网页与游戏客户端连接：必须保持网页打开且对应客户端在线，关闭网页后不执行后台接待。接待记录和拒绝状态保存在服务端，刷新不会丢失，但托管需重新开启。自由托管保留原来的定时主动聊天行为；智能接待没有定时追问或群发动作。

未填写真实 Guide、Discord 或业务资料时，相应推荐不会凭空生成。系统仍可自然回应和澄清需求。没有自动创建外部 Discord 机器人，也不会替管理员承诺价格、交付或服务存在。

## 验证与发布

`npm run test:reception` 包含真实 SQLite 迁移/状态测试、接待 API 权限测试、客户端认领与回执测试、调度测试及桌面/手机 UI 测试。UI 测试需要 Playwright 和 Edge，可通过 `PLAYWRIGHT_MODULE_PATH` 指定模块位置。

发布顺序：生产构建与类型检查 → 接待测试及相关原有 AI 回归 → 确认待执行迁移 → 应用 0016 → 部署现有 Cloudflare Worker → 检查页面、匿名接口拒绝访问、已登录配置读取和真实 AI 模拟。

回滚可恢复上一 Worker 版本；新增表与旧代码兼容，无需删除玩家接待数据。真实玩家发送应以游戏回执为准，模拟测试不代表已向玩家发送。
